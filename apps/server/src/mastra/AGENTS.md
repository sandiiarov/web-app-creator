# Mastra Agent DOX

## Purpose

- Owns Mastra landing-page agent impl + custom server-side streaming protocol.

## Ownership

- `agents/`: landing-page agent + memory factories and Studio-discovery config; system prompt has hashline `read`/`find`/`edit` quick-ref + working guidelines. Every agent config wires `inputProcessors` with optional `TokenLimiter` (`@mastra/core/processors`, `config.agentContextTokenLimit` — per-step trimming of oldest non-system messages, backstop) plus `SystemMessagesFirstProcessor` (`lib/system-messages-first.ts`, always last) — a `processLLMRequest` provider-boundary guard that merges all system messages into one leading system message on the wire only: strict OpenRouter upstreams (vLLM chat templates, e.g. Qwen providers AkashML/Chutes/Io Net) HTTP 400 on multiple or mid-prompt system messages ("System message must be at the beginning"), while Mastra emits several (instructions, skills notice, OM context). MessageList keeps its separate system buckets; merge is transient per call. Runtime-owned `Memory` (`@mastra/memory` `Memory` w/ `observationalMemory`, pinned `1.25.0` — 1.26.x needs `storage.patchThread`, absent from core 1.47 + libsql 1.14) owns conversation history: run addresses thread/resource = projectId, sends ONLY the new user message; background Observer/Reflector agents (over the OpenRouter chat default model via `openrouterModel()`, `observeAttachments: false` so image parts stay text placeholders) compress growing history into observations that replace raw messages in context. Observer/Reflector model cost is NOT tracked in run stats. Per-run autocompaction threshold: `/agent` `compactionPercent` (1–100) × `contextWindowTokens(textModel)` → per-call `memory.options.observationalMemory.observation.messageTokens` (min 1_000); omitted when unset/unknown so the OM default applies. No planner — agent implements the user's request directly; the `design` skill is available on demand via the skills workspace.
- `tools/`: Mastra tool factories + landing tool registry — plan/scrape/read/find/edit/generate_image/screenshot. `tools/plan.ts` = simple per-run work plan: the agent writes its approach at run start in free form (any structure; always ends with verification), purely organizational (no statuses, no step schema, no completion gate); re-calling replaces the plan wholesale.
- `lib/`: OpenRouter model/capability/vision/cost helpers, project screenshot capture, anchored HTML editing, tool display, provider compatibility, and runtime-owned project storage. Non-streaming HTTP transport and operation ownership live in `../providers/`.
- `skills/`: on-disk agent skills (currently `design` — SKILL.md + `references/{create,iterate,review}.md`), discovered by the workspace in `workspace.ts`; `build` copies them into `dist/mastra/skills/` so `start` resolves them too.
- `workspace.ts`: factory for a runtime-owned skills-only Mastra `Workspace` — `skills: ['./skills']` + explicit `LocalSkillSource` rooted at this module's dir (cwd-independent; valid from `src/mastra/` in dev + `dist/mastra/` after build); no filesystem/sandbox providers, so the agent gets ONLY the built-in `skill`/`skill_read`/`skill_search` tools (no `mastra_workspace_*` tools). Each Mastra runtime registers its own workspace; per-run factory agents inherit it via their runtime-owned `mastra` reference.
- `route.ts` supplies model/tool execution to the application run coordinator. Successful output records commit before delivery; project metadata uses `turnId:null`, while document commits publish lightweight hashes through the repository so protocol-v2 subscribers can enrich or resnapshot. Each accepted run owns one provider operation scope passed through capability lookup, attachment analysis, tools, capture, OCR, and project-write boundaries. It returns execution/accounting results; it does not own durable acceptance, terminal records, status projection, or run-slot release.
- `create-mastra-runtime.ts`: explicit LibSQL, DuckDB, observability, memory, workspace, and Mastra construction. Detached Observational Memory buffering is disabled so stream metadata settlement covers processor work; compaction is awaited and may add latency before a run terminalizes. Project deletion verifies both thread and OM-record cleanup and remains retryable across partial failure. Disposal shuts observability/Mastra down before closing both stores and attempts every cleanup after partial failures. `index.ts` remains the Studio-discoverable production export.

## Local Contracts

- Agent edits project HTML via the **anchor-label edit engine** (first-party, `lib/anchor-edit/`): lines addressed by STABLE document anchors (`a1`,`a2`,… `a`+base-36 — already in `html.json` `[anchor,text]` + `nextAnchor`), NOT line numbers. ONE version, no toggle. `read`/`find` emit `<anchor> <text>` rows (+ optional `@GEN` checksum marker); `edit` takes STRUCTURED `{ action, edits: [{ start, end, content }] }` — no DSL / `diff` string: `start`/`end` = anchor strings (inclusive span; start==end = one line), `content` = one multi-line string (`\n`-split; empty = delete span). `applyAnchorEdits` (`engine.ts`) splices the doc array via `getDocument`/`setDocument` on `HtmlStoreFilesystem`, preserving untouched anchors + minting fresh ones (`nextAnchor++`) → returns DELTA of new `<anchor> <text>` lines (model reuses every other anchor; rarely re-reads). Staleness = anchor absent → re-read (no tag/snapshot/seen-line gate). Rejects reversed/overlapping spans + unbalanced HTML; truncation repair appends missing closers as fresh anchored lines when nesting is clean (mid-doc mismatch still rejects). Store = write-through `createProjectHtmlStore` over `html.json` (persisted source of truth); tools never mutate repo files, UI never writes HTML. `index.html` = legacy import-only. Live edits stream rendered `html_update` SSE (not persisted into turns). `lib/anchor-edit/` exempt from perfectionist sort + `no-explicit-any` (`apps/server/oxlint.config.ts`); first-party, no external attribution.
- Project title set server-side from first prompt (`setTitleIfUntitled`) on `POST /agent`; `ProjectMeta` persists all three per-role models (`textModel`/`imageModel`/`visionModel`) via `PATCH /api/projects/:id`, while `POST /agent` run-start persists only `textModel`, each saved message turn keeps text model used for that turn. All `project.json` read-modify-writes synchronous (`readMetaSync`/`writeMetaSync`) so model PATCH serializes vs edit-time `markHasHtmlSync` writes w/ no lost update (no `hasHtml` reversion).
- Project conversation history server-owned, persisted as append-only logs, each holds one execution context, appended per event/step (never overwritten) so data at any moment inspectable: (1) `client-messages.jsonl` — client wire (`dir:"out"` = each SSE event; `dir:"in"` = prompt + screenshot POST-back, metadata + file pointer only, never base64); `getProject` `replayClientEvents`-reduces into `ProjectMessageTurn[]` for hydration (each `dir:"in"` prompt starts turn w/ real `turnId`; `done` terminalizes; tools left running terminalized to `error` on restore). (2) `agent-messages.jsonl` — per-step Mastra `messageList` snapshots (`stream.messageList.get.response.db()` via `onStepFinish` + once at run end), sanitized via `sanitizeAgentMessages`: `reasoning` parts stripped (`stripReasoning`) so logs don't inflate + inline `data:image/*` payloads replaced w/ placeholder (`stripInlineImageData`) so direct-mode screenshot bytes never land in JSON logs. INSPECTION-ONLY: agent history is owned by the Observational Memory thread (`mastra.db`, thread/resource = projectId); the run sends ONLY the new user message per the OM contract (replaying full history duplicates stored messages), so no `readAgentRawByTurn` replay path exists anymore. Both logs fall back to legacy `messages.json`/`raw-messages.json` for old projects. (3) `vision-messages.json` — per OCR/vision call (attachment `ocrImageInputs` AND scrape `ocrImages`, both carry `projectId`/`turnId` threaded through `LandingToolContext`), text/usage/cost only. (4) `screenshots/<NNN>-<requestId>.<ext>` — captured screenshot bytes written at POST-back resolve. Prompt image attachments analyzed before OpenRouter agent run (OCR transcript in fallback mode, direct image parts when chat model accepts images); selected-element attachments also pass captured `outerHTML` into agent context alongside screenshot OCR. No base64 image bytes ever written to JSON log.
- User-facing agent text stays concise, uses latest user prompt's language (English when English or ambiguous), must NOT echo internal tool transcripts like `Tool read done`, `Action:`, `Detail:`, or `Result:`; UI renders tool status separately.
- `LANDING_AGENT_INSTRUCTIONS` (`agents/landing-page-agent.ts`) opens working guidelines with the plan-first rule (start every run with the `plan` tool, free-form approach, ends with verification) and includes advisory `HASHLINE_SYSTEM_GUIDANCE` quick-ref from `lib/anchor-edit/edit-prompt.ts`: `<anchor> <text>` reads, structured `edits:[{start,end,content}]`, stable anchors + delta-return, balanced closing tags, failure recovery. Batches complete logical change (whole section, related block, entire fix/refinement) into one `edit` whose `edits` array may carry many ranges, instead of many tiny one-line edits; full finished page in one edit still avoided (`maxOutputTokens` truncation, `finishReason=length`). `screenshot` = final verification/QA step taken once page or requested change complete (like tests/lint), not after every edit; targeted request may screenshot once before to assess current state, once after — never reflex after each intermediate edit.
- Replaces the old v1 line-number/DSL engine (removed). Study: v1 baseline 17.8% edit reject / ~144k wasted out-tokens (283 proj / 482 edits); anchor engine ~11% (0 unseen-line/stale/parse; residual rejects are genuine HTML-imbalance that self-corrects on retry). Verified by agent-browser e2e.
- Every user-visible tool call must include `action`; client renders it in conversation UI. Tools accepting `action` should receive one from agent. The `design` skill is served by the skills workspace (`workspace.ts`): Mastra lists it in the system message and the agent loads it on demand via the built-in `skill`/`skill_read`/`skill_search` tools (handled by `tool-display.ts` skill branches).
- Mastra `tool-result` chunks w/ top-level `{ ok: false }` = terminal failures for custom SSE protocol, must stream + record `tool_call.state = "error"` even when SDK chunk `isError` flag false. `tool_call` payloads carry timing for the UI timer: `startedAt` (epoch ms) on running/start (tracked per provider toolCallId in `run-stream-loop.ts`; one timestamp for `analyze_image` in `route.ts`) and `durationMs` on terminal done/error.
- Observational Memory stream parts (`data-om-observation-start/end/failed`) map to a `memory` SSE event (`{ id, operation: 'observation'|'reflection', state: 'running'|'done'|'error', tokensObserved?, observationTokens?, error? }`) in `run-stream-loop.ts`; the shared reducer upserts a `memory` turn part by cycle id and the client renders a compaction marker (`Marker variant="separator"`) in the conversation.
- `tools/landing-tools.ts` = source of truth for enabled custom tools + construction; built-in `skill*` tools come from the skills workspace, not this registry.
- Additions/removals of tools must update SSE mapping, cost accounting, client event types, this DOX when behavior changes.
- `read`/`find`/`edit` operate on anchors. `read()` → whole doc as `<anchor> <text>` rows (+ optional `@GEN` checksum marker) — no paging/offset/limit, no `[#TAG]`, no snapshot store. `find({ text, regex?, ignoreCase?, context?, limit? })` → matching + context lines as `<anchor> <text>`. `edit({ action, edits: [{ start, end, content }] })` — `start`/`end` anchors inclusive (`start==end` = one line), `content` multi-line string (empty = delete span); one `edit` may batch many non-overlapping ranges. Anchors from latest read/find are stable across edits, so reuse any seen; engine mints fresh anchors only for inserted lines + returns them as a delta. At SSE boundary one `edit` = one `tool_call` block (1:1 — no fan-out, no `tool_call_drop`), carrying top-level `action`; `html_update` once per successful edit. Build incrementally (scaffold → tokens → fill sections), each `edit` = complete logical unit — never full finished page in one edit (`maxOutputTokens` truncation).
- `openrouterModel()` (`lib/openrouter-model.ts`) uses Mastra `OpenAICompatibleConfig` w/ ids shaped as `openrouter/${modelId}` so synthetic prefix stripped, full OpenRouter model id sent verbatim to `openrouter.ai/api/v1/chat/completions`. OpenRouter = only provider for all agent LLM traffic (text brain), image generation, vision OCR. All three roles selectable per request via `/agent { textModel?, imageModel?, visionModel? }`, default from `config.openrouter.default{Chat,Image,Vision}Model`; default chat model + client-provided Text options use OpenRouter's `:nitro` routing variant. Main agent retries configured via `config.agentRetry`; hidden AI SDK model retries default `0` so user-visible Mastra retry events own backoff reporting unless overridden by env.
- `screenshot` tool's `inputSchema` intentionally optional + `.passthrough()`, `execute` runs raw input through `recoverScreenshotArgs` before use. GLM-5.2 intermittently streams `selector`/`viewportSize` wrapped in `<arg_key>`/`<arg_value>` tags that collapse JSON into one mangled key; recovery regex-extracts selector/viewportSize/action (parses JSON-string args) so usable call lands instead of validation error. Keep recovery in `execute` (whole-object `z.preprocess` makes Mastra type tool input as `unknown`).
- Streaming tool-call finalization patched (see root AGENTS + `patches/@mastra__core@1.47.0.patch`): Mastra's actual OpenRouter ESM/CommonJS adapters buffer argument fragments, emit `tool-input-*` + `tool-call` only at end-of-stream, replace initial `{}` placeholder when later cumulative JSON arrives, raise provider-stream error for incomplete final JSON instead of silently coercing to `{}`, and serialize multimodal tool-result `content` outputs as chat-completions `text`/`image_url` parts (direct-mode screenshots). Older generic OpenAI-compatible safeguard remains. `lib/openrouter-tool-stream.test.ts` executes both installed adapters vs placeholder/cumulative + truncated SSE streams; `lib/openrouter-tool-result-image.test.ts` asserts multimodal + plain tool-result wire serialization on both adapters.
- `resolveModelId()` strips optional `openrouter/` prefix, falls back to **chat** default only. Correct for `textModel`, but `/agent` handler must forward `undefined` for omitted `imageModel`/`visionModel` so `streamLandingAgent`'s `StreamOptions` destructuring defaults apply role-specific image/vision models. Routing image/vision through `resolveModelId` silently substitutes chat model (neither image nor vision capable), 404s at provider when callers send only `textModel`.
- Agent generation sampling pinned in `route.ts` `modelSettings` from `config.agentGeneration` (`config-env.ts`): GLM-5.2 temp defaults `1.0` (`AGENT_TEMPERATURE`), or nucleus sampling via optional `AGENT_TOP_P` — only one ever emitted on wire (Z.ai docs say tune EITHER temp OR top_p, never both). `reasoning_effort` intentionally NOT set via the generic OpenAI-compatible path (it drops `providerOptions.openai.reasoningEffort`); optional reasoning control instead flows through `providerOptions.openrouter.reasoning`, which Mastra's OpenRouter adapter spreads verbatim into the wire body: `AGENT_REASONING_MAX_TOKENS` (config `agentGeneration.reasoningMaxTokens`) → `reasoning: { max_tokens }`, else `AGENT_REASONING_EFFORT` (`low|medium|high|none`) → `reasoning: { effort }`. Unset = GLM-5.2 defaults to `max` (deep reasoning, recommended coding/agentic setting). For over-thinking models (qwen 27b) prefer the max-tokens cap: providers may ignore effort in tool-heavy agentic contexts, letting reasoning eat the whole `maxOutputTokens` budget and truncate the step before any tool call (observed: zero-edit runs). `maxOutputTokens` stays `16_384` to keep edits incremental (section-sized, never whole finished page) — large enough for medium-sized cohesive edit, small enough to avoid mid-generation truncation.
- Image delivery to the agent has two modes, picked per run by `supportsImageInput(textModel)` from the bounded OpenRouter catalog lookup: **direct mode** sends screenshot captures and prompt attachments as image parts; **fallback mode** uses the configured OpenRouter vision model for OCR. Every non-streaming OpenRouter, Firecrawl, CDN, and ephemeral-publish request uses the shared provider transport, whose operation deadline covers attempts, abortable backoff, and incremental body consumption. JSON is capped at 16 MiB (48 MiB for encoded image generation), binary image/screenshot bodies at 32 MiB, and error text at 64 KiB. Safe reads may retry transient failures; paid POSTs do not retry after dispatch because no endpoint-specific idempotency guarantee exists. OpenRouter USD cost and Firecrawl credits are recorded immediately after parsing and deduplicated per operation/report, independently of later extraction/download/persistence success. Main streamed LLM raw-chunk cost remains separate. Final Mastra usage and finish reason settle independently within the metadata deadline so a fulfilled usage value is retained when its partner rejects or hangs.
- `scrape` tool (`tools/scrape.ts`) requests Firecrawl formats `{type:'screenshot', fullPage:true}` + markdown/links/images/branding + `{type:'json', prompt:'Describe each image', schema:{images:[{url,description,width,height}]}}`, with `maxAge` 2 days, `parsers:['pdf']`, and model-set `timeout` (default 30s) / `waitFor` (default 0) / `excludeTags` / `includeTags` / `onlyMainContent`. Vision OCR runs on the rendered full-page screenshot w/ the layout prompt (`SCREENSHOT_OCR_PROMPT` + `ui_to_artifact` system) returned as `imageOcr`; per-image-URL OCR is fallback only when Firecrawl returns no screenshot. Structured per-image extraction returned as `imageDescriptions`; signed `screenshot` URL exposed (Firecrawl-signed, expires).
- `screenshot` publishes prepared HTML to the ephemeral host, then starts mobile/tablet/desktop Firecrawl captures together. Each viewport reports credits as soon as Firecrawl parses them, downloads the PNG under the same owned child, and checks its write lease immediately before persistence. One failure aborts siblings and awaits their settlements through the drain grace; siblings that ignore cancellation remain tracked, produce a typed failed drain, and cannot write late. A short mobile capture may retry once under a distinct paid operation, whose known credits survive retry or delivery failure.
- Element attachments carry only `{ kind: 'element', selector }` on wire; uploaded/pasted images still send full payload w/ base64 `dataUrl`. Server's `analyzePromptAttachments` gathers all element selectors, calls one `captureProjectSelectors` batch over current HTML. Direct mode: uploaded data URLs + captured element screenshots become `image` parts on current user message (no OCR/vision cost, `analyze_image` tool_call reports `Attached N image(s) to the model`, no `analysisText` persisted). Fallback mode: flattens three viewport images per selector alongside uploaded image data URLs into one bounded OCR call (records `vision-messages.json` + `analysisText`). Safe persisted screenshot URLs for element captures included in terminal `analyze_image` tool `images` preview; uploaded-image data URLs enriched client-side from attachment state (never sent through durable event log). Element attachment metadata persisted to turns = `{ id, kind: 'element', name, selector }` — no `html`, `mediaType`, `screenshotHeight/Width`, or `size`. Legacy persisted turns w/ old element fields hydrate via backward-compatible optional fields in `ConversationAttachment`.
- No planner call, no `LANDING_PAGE_DESIGN_GUIDANCE` (file deleted). Design guidance lives in the on-disk `design` skill (`src/mastra/skills/design/`: SKILL.md + `references/{create,iterate,review}.md`), served through the skills-only workspace; the agent loads only the lifecycle reference matching the current request.
- Image ids are `img-<uuid>` for new output; legacy `img-<number>` URLs stay readable. The bounded runtime image store rejects capacity instead of evicting bytes required for persistence. Project-bound `generate_image` writes bytes exclusively to `.data/projects/<id>/images/`, flushes file + directory, releases the buffer, and returns the stable project URL before the model sees success. Project-owned lookup still resolves an old temporary URL during the same process or after repository reconstruction for that known project.

- Project repository owns durable identity (`brief`, `title`, `titleSource`) and idempotent draft creation via UUID creationKey. First prompt preserves the full brief; page writes update automatic names from HTML title and broadcast `project_meta` only after the metadata replacement commits; explicit user names never change automatically. Metadata RMW remains synchronous. Legacy identity migrates once on read, retaining custom names. This does not change the HTML edit engine or agent protocol.

## Work Guidance

- For Mastra changes, read installed package docs/types first; Mastra APIs change quickly.
- Keep tests off system-prompt prose. Test hashline parser/tools as executable behavior, use live traces to judge model adherence.
- Keep per-run `Agent` + `HtmlStore` isolation. Mastra Studio visibility uses a discoverable agent owned by the production Mastra runtime.
- Prefer `zod` schemas at tool boundaries, small pure helpers in `lib/`.
